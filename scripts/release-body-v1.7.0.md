## ✨ S5 در یک نگاه

هدف S5: **موتور محاسبات و مسیرهای API هیچ وابستگی‌ای به منطقهٔ زمانی سیستم میزبان نداشته باشند.** ممیزی کامل و مستند انجام شد (`docs/PHASE2-S5-AUDIT.md`)، همهٔ یافته‌ها اصلاح شدند و صحت با اجرای واقعی تست‌ها در **چهار منطقهٔ زمانی** اثبات شد.

## 🩹 اصلاح S4 (شامل در این نسخه)

تأخیر/خروج زودتر از **جفت‌های وابسته به پنجرهٔ شیفت** سنجیده می‌شود؛ جفت‌های سرگردانِ خارج از پنجره (مثلاً عبور ۰۲:۳۰–۰۲:۵۰ روی شیفت عصر ۱۵:۰۰–۲۳:۳۰) دیگر تأخیر واقعی (۲۰ دقیقه) و خروج زودترِ واقعی (۲۰۰ دقیقه) را پنهان نمی‌کنند. دقیقه‌های کارکرد جفت‌های سرگردان طبق قرارداد S4 شمرده می‌شوند و ستون‌های خام اولین ورود/آخرین خروج عیناً همان‌اند. (کامیت 49e71b2b — بازبینی کد تأییدشده.)

## 📜 تغییرات قرارداد تاریخ API (`docs/API-DATE-CONTRACTS.md`)

- **ثبت (write) از این پس سخت‌گیرانه است:** `timestamp` تردد دستی/ویرایش و `startDateTime/endDateTime` مرخصی و ردیف CSV فقط ISO کامل **با** منطقهٔ زمانی (`Z` یا `±HH:MM`) — رشته‌های بدون منطقهٔ زمانی (مثل `2026-11-17T08:30`) ۴۰۰ می‌گیرند (قبلاً خاموش به وقت میزبان تبدیل می‌شدند).
- **فیلتر خواندن ترددها:** `from/to` فقط-تاریخ → پنجرهٔ instant از **نیمه‌شب تهران** روز from تا نیمه‌شب تهران روز to+1 (قبلاً نیمه‌شب UTC).
- **kiosk/me:** پنجرهٔ «امروز» = روز تقویمی واقعی تهران.
- مارکرهای روز (DailyAttendance و…) و قرارداد فقط-تاریخ **بدون تغییر**.
- مثال‌های معتبر/نامعتبر برای همهٔ قالب‌ها در سند قرارداد درج شده است.

## ✅ نتایج تست — گزارش جداگانهٔ ادعا (assertion) و بخش (section)

هر مجموعه زیر **واقعاً** در هر چهار منطقهٔ زمانی `UTC / Asia/Tehran / Europe/Vienna / America/New_York` اجرا شد (اسکریپت `scripts/tz-matrix.sh`؛ ۹ مجموعه × ۴ TZ) و خروجی‌ها هم‌ارز بودند:

| مجموعه | ادعاها | بخش‌ها | وضعیت در هر ۴ TZ |
| --- | --- | --- | --- |
| زیرساخت زمان (`test-time`) | **۱۰۱ سبز / ۰ خراب** | **۲۳ سبز / ۰ خراب** | یکسان (byte-identical) |
| موتور حضور — خالص (`test-attendance`) | **۱۶۳ / ۰** | **۴۹ / ۰** | یکسان |
| موتور حضور — دیتابیس واقعی (`test-attendance-db`) | **۸۹ / ۰** | **۱۶ / ۰** | یکسان |
| ورود خام دستگاه (`test-raw-import`) | **۱۶۷ / ۰** | — | یکسان |
| ناظر Bridge (`test-bridge-supervisor`) | **۲۵ / ۰** | — | یکسان |
| پیکربندی دستگاه (`test-device-config`) | **۷۶ / ۰** | — | یکسان |
| زمان‌بند (`test-scheduler`) | **۲۹ / ۰** | — | یکسان |
| اعلان‌ها (`test-live-notif`) | **۲۸ / ۰** | — | یکسان |
| Polling شبه‌بی‌درنگ (`test-rt-poll`) | **۲۵ / ۰** | — | یکسان |

جمع هر TZ: **۷۹۱ ادعا، ۰ خراب**. بخش ۲۴ ماتریس خروجی S5 (پارسرها، روز هفته، پنجره‌ها، موتور، انتساب روز کاری) را بین چهار TZ بیت‌به‌بیت مقایسه می‌کند. **اثبات تشخیص واقعی:** روی کد قبل از S5 همین مجموعهٔ دیتابیسی زیر `America/New_York` واقعاً شکست می‌خورد (۳ ادعا/۲ بخش — باگ faWeekday) — یعنی سبز شدن به اصلاح واقعی وابسته است نه ضعف تست.

تست‌های HTTP سرور کامل (بوت standalone): نصب تمیز و **ارتقا از دیتابیس pre-S3** هرکدام جداگانه سبز شدند (ورود کاربر قدیمی، ارائهٔ تردد قدیمی در پنجرهٔ تهران، recalc موتور جدید روی دیتابیس ارتقایافته، ۴۰۰ برای ISO بدون timezone، ۴۲۹ تکرار kiosk).

کیفیت: `npx tsc --noEmit` → **۰ خطا**؛ `npx eslint .` → **پاک**؛ `npm run build` → **موفق** (بستهٔ standalone استاندارد).

## 🗄️ دیتابیس، migration و ارتقا

- **S5 هیچ migration جدیدی ندارد** — همهٔ تغییرات S5 در کد است؛ اسکیمای Prisma دست نخورده.
- migrationهای فاز S3 (`scripts/migrate-v1.7.0-phase2-s3.mjs` و `…-s3r2.mjs`) موجود، افزایشی، idempotent و قابل rollback مستند هستند و در تست دیتابیس بررسی شده‌اند (بالا/پایین‌رفتن با حفظ داده).
- **نصب تمیز:** زیپ → `INSTALL.bat` → `START.bat` (Node.js 20+).
- **ارتقا از نسخهٔ قبلی:** فایل‌های جدید را روی پوشهٔ نصب فعلی باز کنید و `INSTALL.bat` را اجرا کنید — دیتابیس موجود تشخیص داده می‌شود، داده‌ها حفظ می‌شوند و فقط بستهٔ جدید build می‌شود (تست واقعی همین مسیر سبز شد).
- **Backup/rollback:** قبل از ارتقا کافی است `db\custom.db` را کپی کنید (کل داده در همان یک فایل SQLite است)؛ برگرداندن = جایگزینی فایل و اجرای دوبارهٔ نسخهٔ قبلی. rollback ساختاری S3 با `node scripts/migrate-v1.7.0-phase2-s3.mjs down --confirm` مستند است (فقط ستون‌های آن فاز را حذف می‌کند؛ ترددها هرگز دست نمی‌خورند).
- هیچ دیتابیس واقعی‌ای در تست‌ها حذف/بازسازی نشده (همهٔ throwaway در پوشهٔ تست).
- DLLهای SDK رسمی FK623 (۷ فایل) همراه بسته در `tools\fkattend-bridge\bin` هستند.

## ⚠️ محدودیت‌های شناخته‌شده

1. **سخت‌افزار:** تست اتصال واقعی NP756+ (دو مسیر FKAttend/SBXPC)، ZKTeco و رفتار دستگاه روی ویندوز، در این محیط اجرا نشده — چک‌لیست پایین برای همان محیط است (طبق همیشه: `tools/fkattend-bridge/CHECKLIST-WINDOWS.md`).
2. ابهام‌های کاری باز (عمداً دست‌نخورده، مستند در TIME-POLICIES): OT روز تعطیل بدون حداقل/گیت، `breakMin` فقط از استاندارد می‌کاهد، اثر مرخصی وسط شیفت روی تأخیر، مأموریت تأخیر را توجیه نمی‌کند.
3. توابع نمایشی لایهٔ قدیمی (`jFormat`/`faDateTime`/…) فریز شده‌اند و دیگر هیچ مصرف‌کنندهٔ زنده‌ای ندارند (S5-A2).
4. ویرایش تعریف شیفت به‌صورت رترواکتیو روی روزهای تاریخی همان شیفت اثر می‌گذارد (قرارداد موجود) — توصیه: غیرفعال‌سازی و ساخت شیفت جدید.

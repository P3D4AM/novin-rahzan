# 🔧 حضور+ (HozorPlus) v1.8.1 — رفع قطعی شکست نصب ویندوزی + سازگاری npm 10 / npm 11

نسخهٔ پیش‌انتشار (Pre-release) — هات‌فیکس نصب‌کننده. اگر INSTALL.bat نسخهٔ v1.8.0 روی ویندوز شما با پیام
«A critical native dependency is missing» یا «Fix the npm scripts policy» شکست می‌خورد در حالی که
اینترنت و Node.js سالم بودند، این نسخه دقیقاً همان مشکل را ریشه‌ای رفع می‌کند.

## 🧯 علت ریشه‌ای شکست نصب v1.8.0 (دو عامل مستقل، هر دو رفع شدند)

### عامل ۱ — تشخیص غلط نام فایل موتور Prisma در `scripts/verify-native.js`

اسکریپت قدیمی فقط نام‌هایی شامل `libquery_engine` را «موتور Prisma» می‌دانست. اما در نصب واقعی ویندوز با
Prisma 6.x فایل موتور این نام را دارد:

```
node_modules/@prisma/engines/query_engine-windows.dll.node
```

پیشوند `lib` فقط در نام‌های targetهای Unix ظاهر می‌شود (`libquery_engine-debian-openssl-3.0.x.so.node`).
نتیجه: **نصبِ کاملاً سالم روی ویندوز «شکست‌خورده» اعلام می‌شد** و نصب متوقف می‌شد. بازنویسی‌شدهٔ v1.8.1:

- تشخیص موتور بر اساس **سیستم‌عامل و معماری واقعی** با الگوی نامِ هر پلتفرم:
  - ویندوز: `query_engine-windows.dll.node` (و نام قدیمی `libquery_engine-windows…dll.node`)
  - لینوکس: `libquery_engine-<distro>.so.node` — هر توزیع (debian/rhel/musl/arch/…)
  - macOS: `libquery_engine-darwin.dylib.node` و `libquery_engine-darwin-arm64.dylib.node`
- دفاع معماری: موتور نامدار arm64 هرگز برای x64 قبول نمی‌شود (و برعکس).
- موتور در **هر دو مکان واقعی** بررسی می‌شود: `node_modules/.prisma/client/` (کپی‌شده توسط `prisma generate`، لازم در runtime) و `node_modules/@prisma/engines/` (رسیده از npm).
- فایل باید **غیرخالی و قابل‌خواندن** باشد — فایل صفر-بایت = دانلود ناقص، با پیام مشخص خودش.
- کلاینت تولیدشده در **مسیر واقعی generator** بررسی می‌شود (`output` از `prisma/schema.prisma` خوانده می‌شود).
- سازگاری نسخهٔ prisma CLI / @prisma/client / @prisma/engines / کلاینت تولیدشده بررسی و اختلاف major/minor هشدار می‌شود.
- **هر پیام خطا علت دقیق را می‌گوید**: نبودِ کلاینت تولیدشده («npx prisma generate»)، نبودِ بستهٔ @prisma/engines («npm install ناقص»)، فایل خالی، فایل غیرقابل‌خواندن، معماری اشتباه — دیگر هیچ خطایی به‌صورت کلی به «اجرای مجدد prisma generate» یا «اصلاح سیاست npm» فرونمی‌ریزد.

### عامل ۲ — ترتیب غلط مراحل INSTALL.bat

`verify-native` قبل از `prisma generate` اجرا می‌شد؛ پس بررسیٔ «کلاینت تولیدشده» در همان لحظه همیشه شکست
می‌خورد (فایل هنوز تولید نشده بود). ترتیب اصلاح شد و **Exit Code هر مرحله** بررسی می‌شود:

| مرحله | عمل |
| --- | --- |
| ۱/۸ | بررسی Node.js (≥ ۲۰) **و npm** — نبودن npm = پیام مشخص PATH |
| ۲/۸ | `npm install --no-audit --no-fund --ignore-scripts=false` |
| ۳/۸ | `npx prisma generate` — شکست → توقف با پیام «Prisma Client generation failed» و علت واقعی |
| ۴/۸ | `node scripts\verify-native.js` — شکست → توقف؛ خطوط [X] همان بالا، علت دقیق هر قلم را می‌گویند |
| ۵/۸ | `npx prisma db push --skip-generate` |
| ۶/۸ | نوشتن `.env` با حفظ کامل متغیرها و Secretهای موجود |
| ۷/۸ | مقداردهی دیتابیس (دیتای موجود به‌طور پیش‌فرض نگه داشته می‌شود؛ بازنشانی فقط با تأیید صریح + Backup) |
| ۸/۸ | بیلد production با قفل همزمانی |

هیچ دستوری در INSTALL.bat وجود ندارد که دیتابیس، `.env` یا دادهٔ کاربر را حذف یا بازنویسی کند (تست ساختاری اثبات می‌کند).

## 📦 سازگاری npm 10 / npm 11 (و آمادهٔ npm 12) — فیلد `allowScripts`

npm 11 هنگام نصب فهرست بسته‌هایی با اسکریپت نصبِ «بررسی‌نشده» را چاپ می‌کند (در محیط واقعی شما: هشت بسته —
@parcel/watcher، @prisma/client، @prisma/engines، @swc/core، es5-ext، esbuild، prisma، sharp) و
`--ignore-scripts=false` این هشدار را حذف نمی‌کند؛ npm 12 همین سیاست را اجباری می‌کند.

راه‌حل رسمی (مستندات `npm approve-scripts`): فیلد **`allowScripts` در package.json** پروژه — تنظیمی Project-level
که npm 10 آن را بی‌صدا نادیده می‌گیرد و **هیچ تنظیم global یا user-levelای از کاربر تغییر نمی‌کند**. هر ۹ بستهٔ
اسکریپت‌دارِ درخت، با خواندن اسکریپت واقعیِ نصب‌شده‌شان بازبینی و تک‌تک تصمیمگیری شد (مستند کامل:
`docs/INSTALLER-NPM-SCRIPTS.md`):

| بسته | تصمیم | دلیل (خلاصه) |
| --- | --- | --- |
| prisma، @prisma/client، @prisma/engines | مجاز | موتور/کلاینتِ لازم برای مراحل ۳/۴/۵ نصب |
| esbuild | مجاز | باینری لازم برای `npx tsx` مرحلهٔ ۷ (db-admin) |
| sharp | مجاز | بایندینگ پردازش تصویر production |
| @swc/core، @parcel/watcher | مجاز | اعتبارسنجی بایندینگ پلتفرم (watcher: اسکریپت به‌طور پیش‌فرض no-op) |
| es5-ext | **غیرمجاز (false)** | اسکریپتش صرفاً گرم‌کردن cache است و خودش خطا را می‌بلعد؛ بسته بدون آن یکسان کار می‌کند — حضورش زنجیرهٔ عمیق ابزار preview ادیتور MDX است |
| unrs-resolver | **غیرمجاز (false)** | check تشخیصی برای زنجیرهٔ eslint (ابزار توسعه)؛ نه نصب‌کننده و نه runtime اپ به آن نیاز دارد |

ورودی‌ها **بدون پین‌نسخه** ثبت شده‌اند تا با تغییرهای patch نسخه‌ها تازه‌نشکن بمانند. `--dangerously-allow-all-scripts`
استفاده نشده است.

## ⚠️ محدودیت‌ها — صادقانه

- **روی ماشین ویندوزی فیزیکی کاربر تست نشده است.** تأیید ویندوزی این نسخه از طریق runnerهای
  `windows-latest` گیت‌هاب (npm واقعی + Prisma واقعی + موتور واقعی `query_engine-windows.dll.node`)
  و از طریق تست‌های ساختاری/واقعی لینوکس انجام شده است. این نسخه به‌عنوان **Pre-release** عرضه می‌شود،
  نه نصب کاملاً تأییدشدهٔ روی سخت‌افزار ویندوزی اختصاصی.
- تست‌های نیازمند دستگاه حضور و غیاب واقعی (سخت‌افزار) تغییری نکرده‌اند و همچنان طبق چک‌لیست
  `tools/fkattend-bridge/CHECKLIST-WINDOWS.md` باید روی ماشین ویندوزی اجرا شوند.
- بیلد ویندوزی ZIP روی لینوکس ساخته شده (از درخت git همین کامیت، با تطبیق فایل‌به‌فایل)؛ خود پروسهٔ نصب
  (`INSTALL.bat`) مخصوص ویندوز است و روی ویندوز واقعی کاربر باید نصب تکرارپذیر را تایید کند.
- فیلد `allowScripts` توسط npm 10 نادیده گرفته می‌شود (بدون خطا)؛ رفتار آن روی npm 12 آینده (که هنوز
  منتشر نهایی نشده) احتمالاً اجباری می‌شود — پوشش فعلی برای آن آماده است.

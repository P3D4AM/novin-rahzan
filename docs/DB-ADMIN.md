# مدیریت دیتابیس — سیاست‌ها و عملیات

> فاز ۱ از برنامهٔ اصلاحات (v1.8.0-dev). این سند رفتار **نصب** و **بخش «تنظیمات ← مدیریت دیتابیس»** را مشخص می‌کند و مرجع سیاست‌های حذف/حفظ داده است.

## اصول ثابت

1. **حجم فایل دیتابیس هرگز معیار تصمیم نیست.** تشخیص «دیتابیس خالی/دارای داده» فقط از **تعداد رکوردهای واقعی** جداول می‌آید (`dbStatus` در `src/lib/db-admin.ts`).
2. **دیتابیس موجود به‌صورت پیش‌فرض حفظ می‌شود.** نصب مجدد/ارتقا هرگز خودبه‌خود چیزی را پاک یا Seed نمی‌کند.
3. **هر عملیات مخرب** (پاک‌سازی یا نصب نمونه) نیازمند **تأیید صریح** است: در نصب‌کننده پاسخ `y` به سؤال جداگانه، در رابط کاربری تایپ عبارت تأیید («پاک‌سازی» / «نصب نمونه») پس از دیدن فهرست دقیق حذف/حفظ.
4. **قبل از هر عملیات مخرب، پشتیبان قابل‌بازیابی** گرفته می‌شود (`VACUUM INTO` — Snapshot سازگار SQLite حتی هنگام اجرای برنامه) و مسیر آن به کاربر نشان داده می‌شود.
5. **همهٔ عملیات در AuditLog ثبت می‌شوند** (`DB_BACKUP` / `DB_RESET` / `DB_SEED` / `DB_ADMIN_INIT`) — بدون هیچ رمز یا Secret در جزئیات.
6. عملیات‌ها **تراکنشی**‌اند: خطای وسط کار → بازگشت کامل؛ دیتابیس نیمه‌کاره باقی نمی‌ماند (تست بخش G).
7. قفل درون‌فرآیندی (`withDbAdminLock`) از اجرای هم‌زمان دو عملیات مخرب جلوگیری می‌کند (خطای 409).

## چه چیزی حذف و چه چیزی حفظ می‌شود؟

### حذف می‌شود (داده‌های کسب‌وکار/تراکنشی)

| جدول | محتوا |
| --- | --- |
| `PunchRecord` | ترددهای عملیاتی |
| `RawPunch` | ترددهای خام دستگاه |
| `RejectedRecord` | رکوردهای قرنطینه |
| `DailyAttendance` | کارکرد روزانه (دادهٔ مشتق) |
| `LeaveRequest` / `OvertimeRequest` | مرخصی، مأموریت، اضافه‌کاری |
| `ShiftAssignment` / `DefaultShiftHistory` | تخصیص شیفت و تاریخچهٔ شیفت پیش‌فرض |
| `Personnel` | پرسنل (لینک کاربرها با `SetNull` جدا می‌شود) |
| `Shift` / `ShiftSegment` / `ShiftRotation` | تعریف شیفت‌ها |
| `LeaveType` / `Holiday` | انواع مرخصی، تعطیلات |
| `Department` / `JobTitle` / `EmploymentType` | ساختار سازمانی |
| `DeviceLog` / `DeviceSyncRun` / `DeviceSyncLock` | لاگ‌ها و سابقهٔ همگام‌سازی |
| `Notification` / `Session` | اعلان‌های باقی‌مانده، نشست‌ها (ورود مجدد الزامی) |

### حفظ می‌شود (پیکربندی نصب — هرگز بازنویسی نمی‌شود)

| جدول | دلیل |
| --- | --- |
| `User` | **دسترسی ورود حفظ می‌شود** — رمز کاربران تغییر نمی‌کند؛ `personnelId` به null جدا می‌شود |
| `Device` | تنظیمات اتصال، IP/پورت، **رمز شبکه** و Blob رمزنگاری‌شدهٔ DPAPI دست‌نخورده می‌ماند |
| `Setting` | نام سازمان، ضرایب، آستانه‌ها، **کلید پیامک و Secretها** |
| `NotificationRule` | قوانین اعلان پیکربندی‌شده |
| `AuditLog` | سابقهٔ ممیزی فقط رشد می‌کند؛ هرگز پاک نمی‌شود (ثبت عملیاتِ خودِ پاک‌سازی هم اینجاست) |

> «دیتابیس خالی» یعنی **بدون داده، نه بدون اسکیما**: جداول، Migrationها و تنظیمات ضروری موجودند (مثل `ot_threshold_minutes`).

## نصب‌کننده (`INSTALL.bat`)

```
[6/8] Initializing database …
  DB_STATE=DATA   ← persons/punches/attendance واقعی موجود است
```

- **`DB_STATE=DATA`:** پیش‌فرض «حفظ داده‌ها». پاک‌سازی + نصب نمونه فقط با پاسخ صریح `y` به سؤال جداگانه انجام می‌شود (با پشتیبان خودکار قبل از عملیات).
- **`DB_STATE=EMPTY`:** سؤال **[1] دیتابیس خالی (پیش‌فرض)** یا **[2] اطلاعات نمونه**.
  - گزینهٔ ۱ → `ensure-admin`: حساب `admin` با **رمز تصادفی ۱۲ کاراکتری** ساخته و در `db\FIRST-LOGIN.txt` کنار دیتابیس نوشته می‌شود (رمز در هیچ لاگ/Audit دیگری ظاهر نمی‌شود). پس از اولین ورود، رمز را تغییر و فایل را حذف کنید.
  - گزینهٔ ۲ → `seed --yes`: پشتیبان ← پاک‌سازی ← دادهٔ نمونه (تست بخش I).

سایر اصلاحات نصب‌کننده:

- **`.env` دیگر بازنویسی نمی‌شود** — `scripts/env-ensure.js` فقط `DATABASE_URL` را به‌روزرسانی/اضافه می‌کند و همهٔ متغیرها و Secretهای موجود را دست‌نخورده نگه می‌دارد (تست J).
- **Build با قفل هم‌زمانی** (`scripts/build-with-lock.js`): Build دوم وقتی اولی زنده است رد می‌شود (exit 2) و **قفل هیچ‌وقت حین Build واقعی حذف نمی‌شود**؛ قفل باقی‌مانده از اجرای قطع‌شده (PID مرده) به `.build-lock.stale-*` بایگانی و ادامه می‌دهد (تست K).
- **تأیید وابستگی‌های Native** (`scripts/verify-native.js`) پس از `npm install --ignore-scripts=false`: موتور کوئری Prisma و esbuild حیاتی‌اند؛ SWC/sharp هشدار (با fallback). سیاست `ignore-scripts` کاربر هم بررسی و گزارش می‌شود.
- **Banner نسخه از `package.json` خوانده می‌شود** (`v!APPVER!`) و بنر اجرای `START.bat` هم همین منبع را چاپ می‌کند — دیگر هیچ نسخهٔ hard-codeشده‌ای برای هم‌گام‌سازی وجود ندارد (ریشهٔ مغایرت banner که در v1.7.0 گزارش شد؛ خود asset منتشرشدهٔ v1.7.0 درست بود — v1.6.0 از اجرای INSTALL قدیمی می‌آمد).

## رابط کاربری (تنظیمات ← مدیریت دیتابیس)

فقط نقش **SUPER_ADMIN** (tab در نقش‌های دیگر اصلاً نمایش داده نمی‌شود؛ API هم `requireRole('SUPER_ADMIN')` دارد).

- **وضعیت:** مسیر فایل، شمارش‌های واقعی، آخرین پشتیبان + فهرست ۱۰ پشتیبان آخر. (حجم فایل فقط «اطلاعات» است.)
- **تهیه پشتیبان:** POST `{action:'backup'}` → Snapshot در `db/backups/` + ثبت `last_backup_at`/`last_backup_path`.
- **پاک‌سازی / نصب نمونه:** دیالوگ **سه‌مرحله‌ای** — (۱) فهرست دقیق حذف/حفظ، (۲) تایپ عبارت تأیید، (۳) اجرا با نمایش نتیجه و محل پشتیبان. دکمه تا تطابق دقیق عبارت غیرفعال است؛ API بدون عبارت صحیح 400 می‌دهد.

## بازیابی دستی پشتیبان

1. برنامه را متوقف کنید (`STOP.bat` یا بستن پنجرهٔ سرور).
2. فایل پشتیبان را از `db\backups\` کپی و به جای `db\custom.db` قرار دهید (نام را `custom.db` بگذارید).
3. `START.bat` را اجرا کنید.

پشتیبان‌ها Snapshot کامل SQLite هستند و با `VACUUM INTO` حتی حین اجرای برنامه به‌صورت سازگار ساخته می‌شوند (تست F: بازکردن پشتیبان و تطابق شمارش‌ها).

## تست‌ها

`scripts/test-db-admin.ts` (اجرای `npm run test:db-admin`) — ۱۰۲ assertion در ۱۱ بخش A..K، همه روی **دیتابیس دورانداخت آزمایشی** (مسیر `scripts/test-db-guard.ts` — دیتابیس واقعی هرگز لمس نمی‌شود). پوشش: تشخیص EMPTY بر اساس رکورد نه حجم؛ bootstrap مدیر با رمز تصادفی؛ Seed با حفظ تنظیمات/دستگاه‌ها/حساب‌ها؛ پاک‌سازی با حفظ کلاس‌های محافظت‌شده؛ پشتیبان قابل‌بازیابی؛ اتمیک‌بودن تراکنش (trigger خطا وسط Seed → rollback کامل)؛ قفل هم‌زمانی؛ CLI نصب‌کننده؛ حفظ `.env`؛ قفل Build زنده/باقی‌مانده.

> اجرای واقعی `INSTALL.bat` روی ویندوز (مسیر batch، winget، فایروال) نیازمند تست روی ماشین ویندوزی است — چک‌لیست پایانی فاز.
